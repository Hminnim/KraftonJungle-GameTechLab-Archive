# Week12 버전 시스템 명세

팀원이 덤프를 열면 **실행됐던 배포를 찾고, 그 배포의 EXE·DLL·PDB와 빌드 당시 소스를 조회**할 수 있다. 이 문서는 수동 배포, 크래시 게시, 서버 파일 구조, 조사와 삭제를 정의한다.

## 실행 순서

1. `Setup/SlnGenerator.bat`을 실행해 `Hitori.slnx`를 생성한다. 생성된 솔루션을 Visual Studio에서 열고 `HitoriEditor`를 빌드하면 `HitoriVersionManager`와 `HitoriCrashReporter`도 같은 구성으로 빌드된다. 저장소를 제공할 PC의 관리자 터미널에서 관리 프로그램으로 공유를 초기화한다. 아래 예시는 레포지토리 루트의 PowerShell에서 Release 도구를 실행한다. 파일은 기본적으로 `%ProgramData%\Week12VersionStore`에 보관한다. 설치 계정에 공유 권한을 부여하며, 다른 팀 계정은 호스트의 공유 및 파일 권한에 추가한다.

   ~~~powershell
   $manager = '.\Build\Bin\Release-windows-x86_64\HitoriVersionManager.exe'
   Start-Process $manager -ArgumentList '--initialize-share' -NoNewWindow -Wait
   ~~~

2. 사용할 Windows 공유 주소를 프로젝트의 `GameConfig/VersionStore.json`에 한 번 설정한다. 특정 설치에서만 바꾸려면 실행 파일 옆 `GameConfig/VersionStore.json`을 사용한다. 관리 화면의 **저장소 설정**은 이 PC에만 적용되는 예외 설정이며, `HITORI_VERSION_STORE`는 실행 환경에서 명시적으로 주소를 덮어쓴다. 아래 명령은 명령줄에서 공유를 확인할 때 사용한다. 노트북 실습 주소는 `\\DESKTOP-6KQUH32\VersionStore`이며, 내부망에서는 새 호스트의 PC 이름으로 바꾼다. 호스트에서 신뢰하는 내부망의 **파일 및 프린터 공유**를 켜면 다른 PC에서도 접근할 수 있다. 심볼 등록·삭제와 Source Link 편집을 할 PC에는 Windows SDK의 Debugging Tools for Windows가 필요하다.

   ~~~powershell
   $env:HITORI_VERSION_STORE = '\\DESKTOP-6KQUH32\VersionStore'
   Start-Process $manager -ArgumentList '--list' -NoNewWindow -Wait
   ~~~

3. Visual Studio에서 평소처럼 `HitoriEditor` 또는 `HitoriGame`을 빌드한다. 기존 `Build\Bin\<구성>-windows-x86_64` 출력 폴더에 EXE와 매니페스트가 생성된다. 예를 들어 에디터 매니페스트는 `HitoriEditor.build.json`이다. EXE별 이름을 써서 에디터와 게임이 같은 출력 폴더를 사용해도 기록을 덮어쓰지 않는다. Git 이름과 이메일을 설정하고, `origin`은 팀 GitHub 저장소를 가리키게 한다.

4. 출력 폴더의 팀용 `HitoriVersionManager.exe`를 연다. 설정된 저장소에 연결되면 **Release 게시**에서 빌드에 기록된 SHA를 확인하고 **새 브랜치** 또는 **현재 브랜치**를 선택한다. 메인 화면의 **게시 기록 검색**은 기존 기록 조회에 사용한다. 두 검색 조건을 비우면 전체 목록을 표시한다. 게시에 사용할 GitHub 계정은 Git Credential Manager에 로그인하거나 프로세스 환경의 `GH_TOKEN` 또는 `GITHUB_TOKEN`으로 제공한다. GitHub 쓰기 권한과 Windows 공유 권한은 각각 필요하다. 기존 빌드를 패키징할 때는 `Package.bat`의 세 번째 인자에 출력 폴더를 넘기면 같은 EXE와 `build.json`이 패키지에 들어간다.

5. 에디터 Output Log에서 **CauseCrash**를 실행하거나 버전 빌드의 EXE를 `-causecrash` 인자로 실행한다. 별도 프로세스가 `MiniDumpNormal`을 `%LOCALAPPDATA%\HitoriCrashReports`에 저장하고 리포트 화면을 연다. **덤프 제출**을 눌러 해당 배포에 덤프를 추가한다. GitHub 쓰기 권한을 확인한 개발자는 활성 배포가 없을 때 Crash 배포와 이슈 작성을 각각 선택할 수 있다. 나중에 게시할 때는 `HitoriCrashReporter.exe`를 직접 실행하거나, 관리 화면의 **로컬 덤프 제출**을 눌러 `.dmp` 파일을 선택한다.

6. 디버거에서 덤프를 열고 심볼 경로를 `srv*\\DESKTOP-6KQUH32\VersionStore\symbols`로 지정한다. 내부망 PC로 옮길 때는 Git으로 도구와 명세를 가져와 새 호스트에서 공유를 만들고 주소를 바꾼다. 기존 덤프·심볼·메타데이터도 옮겨야 한다면 게시 작업을 잠시 중단하고 저장소 전체를 별도로 복사한다.

`HitoriVersionManager.exe`는 팀의 Release 게시와 메타데이터 조회·정리를 맡는다. `HitoriCrashReporter.exe`는 덤프 생성과 제출을 맡으며, 개발자가 선택하면 조사용 Crash 배포와 GitHub 이슈를 생성한다. 두 프로그램은 Win32 창을 직접 만들고 DirectX 11로 Dear ImGui 화면을 그린다. 공유 파일과 GitHub를 처리하는 C++ 코드는 두 실행 파일에 링크된다. 게임 패키지에는 리포터 실행 파일이 포함된다. VS 빌드는 `BuildId`와 소스 SHA를 기록한다. 매니페스트가 없는 과거 빌드에서 난 크래시는 덤프의 모듈 식별 정보로 연결한다.

## 1. 배포, 빌드, 크래시

**배포**는 특정 빌드의 `{ EXE, DLL 목록, PDB 목록, Git 저장소와 커밋 SHA }`를 서버에 등록하고, 조회에 필요한 메타데이터를 남기는 행위다. 일치하는 PDB가 있으면 선택창 없이 함께 등록한다. PDB가 없어도 배포할 수 있다. 소스를 보존하지 못한 과거의 `Crash` 배포는 Git SHA가 비어 있을 수 있다.

| 항목 | 의미 |
|---|---|
| `BuildId` | 빌드 결과 한 벌의 고유 ID. 컴파일·링크에 들어가기 전에 발급하고 실행 파일 또는 실행 파일과 함께 배치한 빌드 매니페스트에 기록한다. |
| `DeploymentId` | 팀 서버에 등록된 배포의 ID. **빌드 하나에는 활성 배포를 최대 하나만 둔다.** 활성 배포가 있으면 기존 배포를 재사용한다. 삭제된 배포의 ID는 이력에 남기며 이후 별도 조사로 게시할 때 재사용하지 않는다. |
| `Git SHA` | 빌드에 사용한 소스 커밋. **배포 ID로 배포를 찾은 뒤 그 메타데이터에서 SHA를 읽는다.** 같은 저장소의 같은 SHA로 여러 빌드를 만들 수 있다. |
| `DumpNumber` | 게시 도구가 공유 카운터에서 받아 크래시 리포트 하나에 붙이는 전역 번호. 여러 덤프가 같은 배포를 가리킬 수 있다. |
| `CrashBranchNumber` | 게시 도구가 공유 카운터에서 받아 크래시 브랜치에 붙이는 전역 번호. 자동 이름은 `crash/<번호>`다. 덤프 번호와 별도로 발급한다. |

`Release`는 사용자가 배포 도구로 의도적으로 게시한 빌드다. `Crash`는 개발 중 크래시가 발생한 빌드를 조사 목적으로 보존한 배포다. 활성 배포는 게시가 완료되어 새 덤프를 연결할 수 있는 배포다. **정식 배포에서 발생한 덤프는 기존 `Release` 배포에 연결한다.** 크래시 사건만으로 같은 빌드에 두 번째 배포를 만들지 않는다. `Debug`와 `Release` 같은 **컴파일 구성**은 별도 필드다.

예를 들어 커밋 `C0`로 빌드한 Debug와 Release 구성 바이너리를 각각 Crash로 게시하면 두 배포가 생긴다. 각 배포의 덤프와 심볼 등록은 별도로 정리하고, 두 배포의 소스 조회는 같은 SHA를 사용한다.

## 2. 저장소와 프로그램

| 구성 | 역할 |
|---|---|
| **심볼 서버** | 팀 서버의 Windows 공유 폴더. `symstore.exe`가 EXE·DLL·PDB를 Microsoft의 조회 구조로 등록한다. 디버거는 덤프의 모듈 식별자로 파일을 요청한다. |
| **소스 서버** | GitHub 저장소. Source Link가 가리키는 특정 커밋의 소스를 제공한다. 팀이 쓰는 GitHub 접근 권한이 적용된다. |
| **메타데이터 저장소** | 팀 서버의 Windows 공유 폴더. 배포·브랜치·덤프·발급 번호·게시 상태를 파일로 보관한다. |
| **덤프 저장 영역** | 메타데이터 저장소에 있는 `.dmp` 저장 공간. 게시가 완료된 덤프는 해당 배포 ID 아래에 저장한다. |
| **VS 빌드** | 기존 빌드 과정에서 스냅샷을 만든 뒤 컴파일하고, 완료 시 EXE 옆에 해당 SHA를 기록한다. |
| **크래시 리포트 프로그램** | 덤프를 생성하고 전송 선택을 받는다. 개발자에게는 Crash 배포와 이슈 생성 선택지도 제공한다. |
| **팀 관리 프로그램** | `HitoriVersionManager.exe`. 팀원 PC에서 Release를 게시하고 공유 폴더의 배포, 브랜치, 덤프를 조회하거나 삭제한다. |

팀 서버의 Windows 공유 폴더(SMB) `\\팀서버\VersionStore` 아래에 `symbols`와 `VersionData`를 둔다. `VersionData`에 메타데이터와 덤프를 보관한다. 게시·관리 프로그램은 팀원 PC에서 이 폴더를 직접 사용하고, 심볼을 등록하거나 삭제할 때 해당 PC의 `symstore.exe`를 호출한다. Source Link의 원격 소스 조회는 GitHub에서 처리한다. [Microsoft 심볼 저장 구조](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/symbol-store-folder-tree) · [MSVC Source Link](https://learn.microsoft.com/en-us/cpp/build/reference/sourcelink?view=msvc-170)

덤프 쓰기는 팀 공유 폴더에 접근할 수 있는 PC에서 한다. 공유 폴더에 접근할 수 없는 이용자는 덤프를 로컬에 저장할 수 있다. Windows 공유·파일 권한으로 읽기, 쓰기, 삭제 가능 여부를 통제한다.

## 3. 빌드와 로컬 스냅샷

**빌드 도구는 컴파일러가 읽은 소스를 보존한다.** 빌드 뒤에 변경한 파일이 크래시 당시 작업 폴더에 있더라도, 게시에는 빌드에서 사용한 버전을 쓴다.

1. 빌드 도구가 `BuildId`, 작업 브랜치명과 기준 커밋을 기록한다.
2. 빌드 입력에 반영되는 로컬 변경이 있으면 임시 Git 인덱스로 별도의 로컬 스냅샷 커밋을 만든다. 자동 커밋 명령에만 도구용 이름 `Hitori Build Snapshot`과 이메일 `snapshot@hitori.invalid`를 지정하므로 개발자 이름·이메일 설정 없이 빌드할 수 있다. 사용자 Git 설정은 변경하지 않는다. 이미 해당 커밋과 빌드 입력이 일치하면 기존 SHA를 재사용한다. 개발자의 작업 브랜치, 스테이징 상태와 원래 작업 폴더의 변경은 그대로 둔다.
3. VS의 기존 C++ 프로젝트가 원래 작업 폴더를 컴파일한다. 빌드 도구는 컴파일 전에 Git 스냅샷을 준비하고 완료 시 작업 브랜치, 기준 커밋 및 빌드 입력이 같은지 다시 확인한다. 입력이 바뀐 경우 새 매니페스트와 최신 빌드 기록을 확정하지 않고 재빌드를 요구한다. 생성 소스나 외부 의존성은 정확한 파일을 원격에서 제공할 수 있는 범위만 Source Link에 연결한다.
4. PDB를 생성하는 경우 빌드에서 실제로 기록되는 소스 경로를 **스냅샷 SHA의 GitHub 파일 URL**에 매핑한다. MSVC 링크에 `/SOURCELINK`를 사용한다. 빌드 직후에는 아직 GitHub에 없는 로컬 SHA를 가리킬 수 있으며, 게시할 때 그 SHA가 조회 가능해진 뒤 PDB를 등록한다.
5. 빌드가 성공하면 EXE 옆에 대상별 `*.build.json`을 쓰고, 별도의 최신 빌드 보존 폴더에도 EXE·DLL·PDB와 `build.json`을 보관한다. 검증된 다음 빌드가 완성됐을 때 최신 슬롯을 교체한다. 빌드 실패 시 이전 성공 빌드에 남아 있던 슬롯을 유지한다.

보존 정책은 **로컬 작업 복제본당 최신 성공 빌드 1개**다. 기존 산출물을 그대로 사용해 링크가 생략된 빌드는 그 산출물의 `BuildId`를 유지한다. 로컬 관리용 DB는 필요 없다. 아래처럼 최신 빌드를 가리키는 파일과 한 빌드의 매니페스트를 둘 수 있다.

```text
local-builds/
├─ latest.json
└─ <BuildId>/
   ├─ build.json
   └─ artifacts/               # 해당 빌드의 EXE·DLL·PDB
```

스냅샷 커밋은 `refs/crash-snapshots/<BuildId>` 같은 로컬 전용 참조로 보존할 수 있다. **덤프만 저장된 상태는 추가 로컬 스냅샷을 보존하는 조건으로 사용하지 않는다.** 새 성공 빌드로 슬롯이 교체된 뒤 이전 빌드가 크래시하는 경우는 5절의 과거 빌드 규칙으로 처리한다. 사용자가 다른 폴더에 보관해 둔 이전 빌드 파일도 그때 사용한 파일임을 확인할 수 있으면 게시에 사용할 수 있다. 이미 공유 저장소에 기록한 게시 입력은 해당 게시 작업에 속한다. [Source Link의 경로 매핑](https://github.com/dotnet/designs/blob/main/accepted/2020/diagnostics/source-link.md)

## 4. 정식 배포

배포 도구는 사용자가 지정한 빌드 하나를 수동으로 게시한다. 사용자는 **현재 작업 브랜치로 게시**하거나 **기준 커밋에서 파생한 새 브랜치 이름을 지정해 게시**할 수 있다.

1. 배포할 소스와 빌드를 확정한다. 현재 브랜치로 push하는 경우 해당 브랜치에 들어갈 커밋과 변경을 게시 화면에서 확인한다. 새 브랜치 방식은 원래 작업 브랜치의 커밋을 이동시키지 않는다.
2. 배포 대상 SHA를 지정한 원격 브랜치에 push하거나, 원격에서 이미 가져올 수 있는 SHA를 재사용한다.
3. 그 빌드의 EXE·DLL·최종 PDB를 찾는다. PDB가 있다면 각 EXE·DLL과 짝이 맞는지 확인하고, Source Link로 연결된 파일은 팀원이 정확한 원격 소스를 가져올 수 있는지 확인한다.
4. `symstore add`로 파일을 등록하고 저장소 ID와 등록 번호를 기록한다. 명령 종료 코드와 실제 등록 결과를 함께 확인한다.
5. 배포 메타데이터를 저장하고 완료 상태로 전환한다. 실패한 작업은 같은 `BuildId`와 게시 요청으로 재개한다.

이미 만든 빌드에 대해서는 **그 빌드의 소스**를 게시한다. 게시 직전 작업 폴더를 새로 커밋했다면 이전 바이너리와 연결하기 전에 소스 일치를 확인한다. `crash/*`에서 고친 코드를 정식 배포하려면 필요한 변경을 배포 대상 작업 브랜치에 반영하고, 그 커밋으로 새로 빌드해 `Release`를 게시한다. `crash/*` 자체에서 직접 `Release`를 게시하는 흐름은 사용하지 않는다.

## 5. 크래시 발생과 크래시 배포

### 덤프 생성과 접수

Visual Studio에서 직접 저장한 덤프도 **로컬 덤프 제출**에서 `.dmp` 파일을 저장한 이름 그대로 선택해 제출할 수 있다. 기존 배포가 있으면 덤프의 실행 이미지 정보로 연결한다. 크래시 직후 제출과 나중 제출에는 같은 기준을 적용한다. 새 Crash 배포가 필요하면 도구가 최신 버전 빌드와 원래 EXE 경로를 확인한다. 자동 리포터는 실행 시 기록한 경로를 사용하고, 수동 덤프는 모듈 목록에 기록된 로컬 경로를 사용한다. 파일이 덤프와 일치할 때만 사용하며, 원래 빌드 폴더에 일치하는 매니페스트가 있으면 그 빌드의 SHA를 보존한다.

1. 에디터와 게임은 시작할 때 창 없는 덤프 수집기를 실행한다. 수집기는 크래시 이벤트와 대상 프로세스 종료를 함께 기다린다. 정상 종료 또는 디버거 중지로 대상이 종료되면 수집기도 종료한다. 디버거가 대상을 일시 정지하거나 분리한 뒤 대상이 계속 살아 있으면 수집기는 계속 대기한다.
2. 메인 스레드와 Hitori가 직접 만드는 워커는 스택 오버플로 때 쓸 예외 처리 공간을 확보한다. 처리되지 않은 예외가 나면 에디터나 게임은 예외 스레드와 문맥을 수집기에 전달하고 대상이 살아 있는 상태에서 최대 30초 대기한다. 수집기가 `MiniDumpNormal`을 저장한 후 제출 창을 띄운다. 덤프는 **크래시 직후나 나중에** 제출할 수 있다. 게시 가능 여부는 연결할 배포나 빌드 산출물의 존재와 공유 폴더 접근 가능 여부로 판단한다. Git·GitHub 작업과 공유 폴더 쓰기는 게시 단계에서 수행한다.
3. 먼저 `BuildId`나 검증된 모듈 식별자로 활성 배포를 찾는다. 있으면 그 배포에 연결한다. 없다면 개발자는 **이 빌드를 Crash로 게시**해 해당 덤프를 붙일 수 있다. 일반 이용자는 활성 배포에 덤프를 게시할 수 있다.
4. 활성 배포가 없고 Crash 배포를 완료할 수 없으면 덤프 게시가 실패한다. 필수 요소가 없다는 이유를 표시하고 덤프 파일은 로컬에서 다시 선택할 수 있게 둔다. Crash 배포가 먼저 성공해야 덤프를 게시 완료로 기록한다. 같은 파일을 여러 번 제출해도 서버는 매번 새 덤프 번호를 발급한다. 덤프의 SHA-256은 복사 검증에 사용한다.

`BuildId`는 실행 파일 또는 빌드 매니페스트에서 읽고, 덤프와 함께 보낸다. 자체 미니덤프 스트림에 넣는 것도 가능하다. 덤프의 모듈 정보는 바이너리와 PDB가 맞는지 확인하는 데 사용한다. [Microsoft MiniDumpWriteDump](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/nf-minidumpapiset-minidumpwritedump) · [미니덤프의 모듈 정보](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ns-minidumpapiset-minidump_module)

### 새 Crash 배포에 필요한 파일

- **필수 바이너리**는 크래시가 난 원래 EXE와 **덤프에 로드된 것이 확인된 팀 빌드 산출물 DLL**이다. 빌드 매니페스트로 팀 빌드 산출물을 확인하고, 덤프의 모듈 목록과 대조한다. 이미 심볼 서버에 동일 모듈이 있으면 저장본을 재사용하고 새 배포의 SymStore 등록에도 포함한다. 그래야 기존 배포를 삭제해도 새 배포가 사용하는 파일이 남는다.
- EXE의 PE import 목록은 직접 참조를 확인하는 보조 자료다. DLL이 가져오는 다른 DLL이나 런타임에 `LoadLibrary`로 선택해 로드한 DLL은 EXE의 일반 import 목록에 모두 나오지 않는다. 그 순간 로드된 모듈은 덤프의 모듈 목록으로 확인한다.
- Windows 시스템 DLL과 팀이 별도로 배포하지 않는 환경 제공 DLL은 Crash 배포의 필수 업로드 대상에서 제외한다. 필요하면 분석 시점에 해당 바이너리나 심볼을 따로 확보한다. 일치하는 PDB는 발견되는 대로 자동 등록하며, 누락은 게시 실패 사유가 아니다.

[Microsoft PE 형식](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) · [런타임 DLL 로딩](https://learn.microsoft.com/en-us/windows/win32/dlls/run-time-dynamic-linking) · [미니덤프 모듈 목록](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ns-minidumpapiset-minidump_module_list)

### 빌드 소스가 남아 있는 경우

- **덤프에 대응하는 검증된 빌드 기록의 커밋이 로컬 Git에 남아 있으면** 게시 요청으로 크래시 브랜치 번호를 발급받고, 그 커밋을 `crash/<번호>`로 push한다. 최신 스냅샷 슬롯이 교체됐더라도 커밋이 남아 있는 동안에는 사용할 수 있다. 이미 정확한 커밋이 원격에 있는 경우 그 SHA를 사용한다.
- 번호를 발급받은 뒤 같은 이름을 원격에서 확인한다. 동일 게시에서 이미 만든 브랜치라면 재사용한다. 다른 작업의 브랜치가 같은 이름을 사용 중이면 건너뛸 새 번호를 받는다. 조회 실패와 브랜치가 없는 상태는 구분한다. 이미 게시한 스냅샷 커밋은 같은 요청을 재시도할 때 그대로 사용한다.
- 기존 EXE·DLL과 맞는 PDB에서 소스 링크가 그 정확한 SHA를 가리키는지 확인한다. `symstore` 등록을 마치고 `Crash` 배포를 완료한 뒤 해당 덤프를 연결한다. 원래 작업 브랜치와 기준 커밋도 기록한다.

### 과거 빌드의 소스가 남아 있지 않은 경우

| 확인 결과 | 처리 |
|---|---|
| 배포가 이미 서버에 있음 | 기존 배포에 덤프를 연결한다. |
| 배포는 없지만 정확한 소스가 GitHub에 있음 | 그 SHA를 사용한다. 원래 EXE와 해당 빌드에 필요한 DLL이 있으면 `Crash`로 게시할 수 있다. |
| 빌드에 사용한 소스를 어디에서도 확인할 수 없음 | 원래 EXE와 필수 DLL이 있으면 `Crash/_without-source/<DeploymentId>/`에 게시한다. 배포에 `source.status = unavailable`, `source.commitSha = null`을 기록한다. |
| 배포가 없고 원래 EXE 또는 필수 DLL이 없음 | Crash 배포와 덤프 게시를 완료할 수 없다. 빠진 파일을 표시하고 덤프는 로컬에서 다시 선택할 수 있게 둔다. |

PDB는 소스가 없어도 등록한다. 소스 텍스트를 열 수 없는 경우에도 PDB에 들어 있는 함수명, 소스 경로와 줄 번호, 변수의 이름과 타입은 분석에 쓸 수 있다. 변수 값은 덤프가 해당 데이터를 담고 있을 때 볼 수 있다. PDB가 없으면 해당 모듈의 심볼 누락을 표시하고, 확보한 데이터로 콜스택과 디스어셈블리를 조사한다. [Microsoft PDB의 디버그 정보](https://learn.microsoft.com/en-us/windows/win32/debug/symbol-files)

Source Link는 **파일 경로를 원격 파일 URL에 연결하는 규격**이다. 원격 소스가 없음을 알리는 별도의 플래그는 정의하지 않는다. 해당 파일을 가리키는 매핑이 없으면 디버거는 그 파일에 대해 Source Link로 요청할 URL을 얻지 못한다. 디버거에 별도로 설정한 로컬 소스 조회는 가능하다. 관리 화면에는 배포 메타데이터의 `unavailable` 상태를 사용한다. [Microsoft Source Link 규격](https://github.com/dotnet/designs/blob/main/accepted/2020/diagnostics/source-link.md#source-link-file-specification)

PDB가 정확한 커밋을 가리키고 그 커밋이 로컬에만 있으면 해당 커밋을 push해 링크를 살릴 수 있다. 정확한 소스를 잃어버렸다면 해당 PDB는 심볼 분석에 사용하고, 관리 화면은 `소스 없음`을 표시한다. 빌드 기준 커밋이 실제 소스와 일치한다고 확인할 수 없다면 이력 정보로만 저장한다.

`_without-source`의 PDB에 확보하지 못한 소스를 가리키는 Source Link 매핑이 있으면 **게시본의 해당 URL을 GitHub에서 파일이 없다고 확인한 경로로 교체**한다. 예를 들어 `https://raw.githubusercontent.com/<소유자>/<저장소>/<고정-SHA>/.week12-source-unavailable/*`처럼 고정된 커밋의 존재하지 않는 디렉터리를 사용해 GitHub에서 `404 Not Found`가 반환되게 한다. URL에 넣는 SHA는 404 응답을 위한 참조이며, 배포의 소스 SHA는 계속 비어 있다. 유효한 매핑은 유지하고, 이미 매핑이 없는 파일에는 URL을 추가하지 않는다. PDB의 함수명, 줄 번호와 원래 EXE의 짝은 보존한다. 디버깅하는 사람은 일반 분석 절차로 PDB를 로드한다.

원격 조회의 인증·네트워크 오류는 재시도 상태다. 정확한 원격 소스가 없다고 판단한 경우에만 이 경로를 사용한다. 기존 Source Link URL을 교체한 PDB가 원래 덤프와 EXE에 맞는 것은 실습에서 확인했다. **Visual Studio에서 404 응답 뒤의 표시, PDB 로드 유지, 이미 캐시된 PDB 처리**는 구현 검증 항목이다.

### 종료한 조사와 관련된 덤프가 늦게 들어오는 경우

활성 배포에 매칭되는 덤프는 그 배포에 연결한다. 기존 조사가 종료됐고 활성 배포가 없어 **새 Crash 배포가 필요한 경우**, 종료한 조사는 그대로 둔다. 정확한 소스 SHA가 있으면 새 `crash/<번호>` 브랜치에서 게시한다. 동일 요청에 예약한 브랜치는 재시도에 재사용한다. 소스 SHA가 없으면 `Crash/_without-source/<DeploymentId>/`에 새 배포를 등록하고 덤프를 연결한다. 이 경로에서는 Git 브랜치를 생성하지 않는다.

## 6. 메타데이터 파일 구조와 발급 번호

`Crash`에는 최초 크래시 브랜치 폴더들이 있다. 브랜치 폴더 아래에는 해당 브랜치에서 게시한 **커밋 폴더와 직계 자식 브랜치 폴더**를 둘 수 있다. 같은 브랜치의 커밋 폴더는 나란히 놓는다. 각 커밋 폴더에 배포별 디렉터리를 만들고 덤프를 해당 배포 아래에 둔다.

```text
VersionData/                               # 팀 서버의 메타데이터 및 덤프
├─ Release/
│  └─ <DeploymentId>/
│     ├─ deployment.json
│     └─ dumps/<DumpNumber>/{dump.json, crash.dmp}
└─ Crash/
   ├─ counters.json                        # 다음 크래시 브랜치 번호, 다음 덤프 번호
   ├─ _resolved/<BranchId>.json             # 정리한 브랜치의 해결 기록
   ├─ _without-source/<DeploymentId>/       # 빌드 당시 소스가 확인되지 않은 배포
   │  ├─ deployment.json
   │  └─ dumps/<DumpNumber>/{dump.json, crash.dmp}
   └─ <BranchId>/
      ├─ branch.json
      ├─ commits/<SHA>/<DeploymentId>/
      │  ├─ deployment.json
      │  └─ dumps/<DumpNumber>/{dump.json, crash.dmp}
      └─ children/<ChildBranchId>/
         ├─ branch.json
         ├─ commits/<SHA>/<DeploymentId>/
         └─ children/
```

폴더 키는 도구가 발급한 ID와 검증된 전체 SHA를 사용한다. `crash/123` 같은 실제 Git 브랜치 이름은 `branch.json`에 저장한다. 이렇게 하면 브랜치명 속 슬래시가 폴더 계층을 암묵적으로 정의하지 않는다. **Git의 커밋 부모와 업무상 브랜치 부모는 따로 기록한다.** 도구 밖에서 만든 브랜치를 자식으로 포함하려면 팀원이 부모를 명시해 등록할 수 있다.

| 파일 | 주요 필드 |
|---|---|
| `branch.json` | `branchId`, 저장소 ID, 브랜치 이름, `parentBranchId`, 분기 기준 SHA, 최초/최근 게시 SHA, 조사 상태 |
| `deployment.json` | `deploymentId`, `buildId`, 유형, 게시 당시 브랜치 ID·이름, 작업 브랜치·기준 SHA, 소스 저장소·SHA·상태, 타깃·구성·아키텍처, 모듈 목록, 심볼 저장소 ID·경로·등록 번호 목록, 게시자·시각·상태 |
| `dump.json` | `dumpNumber`, `submissionId`, `buildId`, `deploymentId`, 파일 위치·크기·해시·덤프 유형, 발생·접수 시각, 예외 정보가 있을 때 그 요약 |
| `counters.json` | `nextCrashBranchNumber`, `nextDumpNumber` |
| `_resolved/<BranchId>.json` | 저장소, 브랜치 ID·이름·부모 ID, 조사 종료 시점의 SHA, 종료 시각·처리자, 관련 이슈 또는 과거 기록을 찾을 정보 |

도구는 공유 폴더의 배타적 파일 잠금을 얻은 상태에서 카운터를 읽고 갱신한다. 셋업에서 시작 번호를 정하며, 실패·삭제로 빈 번호가 생겨도 재사용하지 않는다. **SymStore 등록 번호는 SymStore가 따로 발급**하므로 팀의 두 카운터에 섞지 않는다. 번호와 완료 여부는 재시도할 수 있도록 공유 작업 기록에 남긴다.

모듈 목록에는 파일 이름, 빌드 산출물 기준 상대 경로, 파일 종류와 조회에 필요한 식별 정보를 기록한다. Windows 바이너리와 PDB는 각각의 조회 키를 갖는다. 게시 메타데이터에는 실제로 등록한 파일만 성공으로 기록한다. [Microsoft의 파일별 조회 키](https://learn.microsoft.com/en-us/windows/win32/debug/using-symstore)

## 7. 조회와 브랜치 조사

- **배포 열기**는 `DeploymentId`로 한다. 배포 메타데이터에서 심볼 등록과 정확한 소스 SHA를 조회한다.
- **브랜치 검색**은 선택한 브랜치와 모든 자손 브랜치를 조회한다. 자식에서 검색을 시작하면 부모와 형제의 배포는 검색 범위에 포함되지 않는다. 배포마다 실제 게시 당시 브랜치를 표시한다.
- **커밋별 보기**는 두 맥락을 제공한다. 브랜치 트리 안에서는 그 브랜치에서 해당 SHA로 게시한 배포를 묶는다. 별도의 저장소·SHA 조회에서는 같은 커밋을 쓰는 모든 배포를 확인할 수 있다. 저장소 전체 커밋 조회는 소스 공유 여부를 파악하는 데 쓰고 삭제 범위로 암묵적으로 사용하지 않는다.
- 크래시 브랜치에 조사와 수정 커밋을 계속 쌓을 수 있다. 예를 들어 `crash/123`에서 `C0`, `C1`, `C2`로 작업했어도 `C0`의 기존 PDB와 배포는 계속 `C0`를 사용한다. `C2`를 빌드해 게시하면 새 배포가 생긴다. 조회 목록에는 실제로 게시된 배포만 나타난다.
- 이슈에는 사건 설명과 덤프·배포 링크, 재현에 필요한 고정 SHA를 남긴다. 팀원은 당시 소스를 조사하고, 필요한 수정만 작업 브랜치로 가져갈 수 있다.

## 8. 권한과 GitHub 이슈

| 사용자 | 도구에서 할 수 있는 일 |
|---|---|
| 일반 이용자 | 공유 폴더 쓰기 권한이 있으면 기존 배포에 연결할 덤프 게시. 공유 폴더에 접근할 수 없으면 로컬 저장 |
| 팀 계정으로 로그인한 담당자 | 팀의 배포·덤프 조회, 분석 |
| 이슈 생성 권한이 있는 개발자 | 크래시 화면에서 `GitHub 이슈도 생성`을 선택하고 제목·본문 작성 |
| 배포 게시 권한이 있는 개발자 | `Release`와 `Crash` 게시 |
| 삭제 권한이 있는 담당자 | 관리 프로그램에서 덤프·배포 정리, 조건을 충족한 브랜치 조사 종료 |

**개발자**는 원본 GitHub 저장소에 쓰기 권한이 있는 계정으로 정의한다. 게시 도구가 사용자의 GitHub 로그인과 원본 저장소 권한을 확인해 개발자 기능을 표시한다. 포크 PR만 보낼 수 있는 계정은 이 기준에서 제외한다. 브랜치 생성·push에는 GitHub의 저장소 규칙이, 공유 파일 쓰기·삭제에는 Windows의 공유·파일 권한이 적용된다. [GitHub 저장소 역할과 쓰기 권한](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)

이슈 생성은 **개발자가 선택한 때에만** 게시 도구가 해당 사용자의 GitHub 인증으로 원본 저장소에 요청한다. 도구가 덤프 번호, 배포 정보와 팀 전용 UNC 경로를 이슈에 기록할 수 있다. 덤프 원본은 공유 폴더에서 제공한다. 개발자는 일반 이용자의 접수 건도 검토한 뒤 따로 이슈를 만들 수 있다. Git 브랜치 생성 및 push도 개발자 PC의 게시 도구가 해당 개발자의 인증으로 수행한다. 이슈 URL과 생성 상태는 GitHub에서 확인한다. 같은 덤프로 이슈 작성을 요청하면 GitHub 이슈 본문의 제출 ID를 확인해 중복 생성을 막는다. [GitHub 이슈 생성 API](https://docs.github.com/en/rest/issues/issues#create-an-issue)

## 9. 덤프, 배포, 브랜치의 삭제

### 덤프 삭제

덤프 삭제는 **그 덤프에 대한 처리 완료**로 기록한다. GitHub 이슈의 해결 처리나 Git 브랜치 조사는 별도 상태다. 관리 프로그램이 공유 저장소에서 삭제 범위를 확인한 뒤 파일과 기록을 갱신한다. 실제 파일 변경 가능 여부는 Windows 권한으로 결정한다.

| 명령 | 실제 삭제 범위 |
|---|---|
| 개별 덤프 삭제 | 선택한 덤프 번호 하나 |
| 배포 단위 덤프 삭제 | 선택한 `DeploymentId` 아래의 모든 덤프 |
| 커밋 단위 덤프 삭제 | **선택한 브랜치 폴더 아래의 해당 SHA 폴더**에 있는 배포들의 덤프. 다른 브랜치의 같은 SHA 폴더는 유지 |
| 브랜치 단위 덤프 삭제 | 선택한 브랜치와 자손 브랜치의 배포에 연결된 덤프 |

위 네 명령은 덤프를 지우는 기능이다. **배포 자체를 삭제하는 명령**과 별도로 표시한다. 같은 브랜치의 같은 SHA에 여러 배포가 있으면, 덤프가 0개가 된 배포를 각각 정리 후보로 표시한다. 배포 전체 삭제는 각 배포 ID를 명시해 확인한다.

### 배포 삭제

배포 자체를 삭제하면 해당 배포에 연결된 덤프를 모두 삭제하고, 메타데이터에 보관한 등록 번호로 `symstore del`을 요청한다. 다른 배포가 등록한 같은 모듈 파일의 참조는 `SymStore`가 관리한다. GitHub의 소스 커밋과 브랜치, 나머지 배포의 덤프와 등록 번호는 유지한다. 아직 배포된 실행 파일을 사용하는 사람이 있거나 검증 중인 경우 담당자가 보관할 수 있다. [Microsoft SymStore 트랜잭션](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/symstore-transactions)

`Crash`의 **선택한 브랜치·커밋 폴더에서 마지막 덤프를 삭제**하면 **‘연결된 배포도 삭제할까요?’**를 표시한다. 배포가 여러 개면 각 배포 ID를 보여주고 정리할 대상을 고르게 한다. SHA가 없는 배포는 그 배포의 마지막 덤프를 기준으로 안내한다. 기본 선택은 배포 유지다. 일괄 삭제와 배포 삭제는 화면에 대상 ID, 덤프 수와 영향받는 자식 브랜치를 보여주고, 정확한 ID를 입력하는 확인을 적용한다. 관리 프로그램은 공유 잠금을 획득한 뒤 실행 범위를 재확인하고, 확인 이후 새 덤프가 추가됐으면 변경된 범위를 다시 보여준다.

### 크래시 브랜치 정리

자기 브랜치와 모든 자손에서 덤프가 없으면 담당자가 **조사 종료**를 선택할 수 있다. 게시와 종료는 같은 공유 잠금을 사용한다. 중단돼 남은 `pending` 또는 `failed` 작업은 종료 확인 창에 함께 정리할 개수로 표시한다. 확인 후 해당 작업의 미연결 심볼 등록과 임시 파일을 정리하고 작업을 닫는다. 덤프 수가 0이 된 순간에는 정리 후보로만 보여준다. 정리 대상 배포를 정리한 뒤 브랜치 폴더를 비우기 전에 `_resolved`에 해결 기록을 저장한다. 이후에도 당시 브랜치명으로 검색하면 해결 상태를 조회할 수 있다.

**이 도구의 삭제 범위에는 원격 Git 브랜치·태그·커밋 삭제를 넣지 않는다.** 동일 SHA를 쓰는 다른 배포나 조사 중인 자식 작업이 있을 수 있다. Git 브랜치 정리를 나중에 사람이 수행하더라도, 남아 있는 배포의 Source Link가 가리키는 커밋은 원격에서 계속 조회할 수 있게 보존한다. [Git 커밋의 참조와 접근 가능성](https://git-scm.com/docs/user-manual.html)

## 10. 실패와 재시도

| 상황 | 동작 |
|---|---|
| 게시 도구 누락 | 새 배포에 필요한 `symstore.exe`와 필요한 경우 `pdbstr.exe`를 브랜치 생성과 작업 기록 전에 확인한다. 설치할 구성 요소를 안내한다. |
| 덤프 생성 실패 또는 오프라인 | 실패 이유를 표시한다. 생성된 로컬 덤프는 다시 선택해 제출할 수 있다. 서버에 먼저 올라간 덤프가 있으면 기존 기록도 남는다. |
| Git push 실패 | 덤프 접수 상태와 분리해 표시한다. 인증·네트워크·브랜치 정책·이름 충돌 원인을 보고한다. 같은 입력이 남아 있으면 실패 단계부터 재개한다. |
| push 성공 후 심볼 등록 실패 | 원격 브랜치와 고정 SHA를 작업 기록에 남기고 심볼 등록을 재시도한다. |
| 심볼 등록 후 메타데이터 저장 실패 | 등록 번호 및 작업 ID를 복구해 메타데이터 기록을 마치거나 해당 등록을 정리한다. 확인 전에는 배포 완료로 표시하지 않는다. |
| GitHub 이슈 생성 실패 | 덤프 접수를 유지한다. 응답이 유실됐으면 제출 ID나 덤프 번호로 기존 이슈를 찾은 뒤 재시도한다. |
| 접수와 삭제가 겹침 | 도구가 공유 잠금 안에서 최종 삭제 범위와 원래 요청을 비교한다. 연결할 활성 배포가 사라졌으면 5절의 Crash 배포 조건을 다시 확인한다. 조건을 충족하지 못하면 덤프 게시를 완료하지 않는다. |
| 삭제 도중 일부 단계만 성공 | 삭제됨과 정리 실패를 구분하고 남은 작업을 재시도한다. 원래 번호나 대상을 다른 항목에 재사용하지 않는다. |

`SymStore`의 `add`와 `del`은 **저장소별로 순서대로** 실행한다. 같은 공유 저장소를 여러 PC에서 변경하는 도구는 동일한 공유 잠금을 사용한다. 기록이 여러 파일에 걸쳐 바뀌면 공유 폴더에 게시·삭제 작업 기록을 남겨 중단 후 상태를 확인할 수 있게 한다. [Microsoft SymStore 트랜잭션 제약](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/symstore-transactions)

배포는 `게시 중`, `게시 완료`, `게시 실패`, `삭제 중`, `삭제 완료`, `정리 실패`를 구분한다. 덤프의 전송과 이슈 생성은 각각 진행 상태를 기록한다. 이슈 생성 요청 실패가 이미 게시된 덤프의 성공 상태를 바꾸지 않는다.

## 11. 구현 검증과 남은 선택

### 수용 기준

1. 미커밋 변경이 있는 상태로 빌드해도 작업 브랜치와 스테이징이 바뀌지 않는다. 빌드 후 원래 파일을 편집하고 이전 EXE를 크래시시켜도 덤프의 `BuildId`와 일치하는 스냅샷만 게시할 수 있다.
2. 뒤이어 성공한 빌드가 최신 로컬 슬롯을 교체한다. 이전 빌드에 대응하는 검증된 SHA가 로컬 Git과 GitHub 양쪽에 없으면 원래 EXE와 필수 DLL이 있을 때 `Crash/_without-source`에 배포할 수 있다. 일치하는 PDB가 있으면 자동 등록하고, 없어도 배포가 완료된다. 활성 배포가 없고 필수 바이너리도 부족하면 덤프의 게시 요청을 거절한다.
3. 같은 SHA의 두 빌드는 별도 배포로 보이고, 같은 빌드 게시 재시도는 기존 배포를 재사용한다. 정식 배포 사용자의 크래시는 그 배포에 직접 붙는다.
4. 자손 검색은 부모에서 자식 방향으로 진행된다. 자식 검색의 결과에 부모나 형제 배포가 섞이지 않는다. 조사 브랜치가 새 커밋으로 전진해도 과거 배포의 SHA는 유지된다.
5. 두 브랜치의 커밋 SHA가 같아도 한 브랜치의 커밋 폴더에서 한 삭제는 다른 브랜치에 영향을 주지 않는다. 브랜치 범위 삭제에는 명시적으로 자손이 포함된다.
6. 커밋 폴더의 마지막 덤프 삭제는 연결된 배포들의 정리 제안까지만 만든다. 담당자가 조사 종료를 선택하고 브랜치 폴더를 정리하면 해결 기록이 남으며 GitHub 소스는 그대로다.
7. 일반 이용자의 프로그램에는 이슈 작성과 Git push 기능이 노출되지 않는다. Windows 공유 권한으로 파일 변경 범위를 확인하며, 개발자의 같은 이슈 생성 재시도는 이슈 한 건으로 처리된다.
8. 동시 덤프 접수와 배포 게시에서 중복 번호가 발급되지 않는다. 네트워크 응답 유실과 중간 단계 실패 뒤에도 동일 요청을 이어서 처리할 수 있다.

### 아직 선택할 구현 항목

- 덤프 업로드 크기 한도, 로컬 덤프와 서버에 게시한 덤프의 보관 기간, `Release` 심볼 보관 기간은 미정이다. 크래시가 난 시점에서 시간이 지났다는 이유로 게시를 제한하지 않는다.
- Git 스냅샷에 포함할 빌드 입력 범위 및 Git 밖에서 생성되는 소스를 제공하는 방식. 이미 덤프가 생긴 과거 빌드를 보존하는 추가 예외는 현재 적용하지 않는다.
- Visual Studio에서 소스 없음 전용 URL의 404 응답을 받았을 때 소스 열기만 실패하고, 원래 PDB의 심볼과 줄 번호는 계속 사용할 수 있는지 검증한다. 같은 PDB 식별자의 이전 게시본을 캐시한 경우도 확인한다.
